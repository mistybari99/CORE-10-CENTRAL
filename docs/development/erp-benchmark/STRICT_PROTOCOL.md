# Mandatory agent maintenance and change-control protocol
Owner instruction, 2026-11-24. Applies to every human/AI research and build participant (ChatGPT, Codex, Claude, other agents and scheduled jobs) within this program. This is an Owner-directed rule proposal in Draft PR #157 until canonical integration; it does not grant permissions or replace the existing Board/Decision Book/release protocol.

## M01 — Authority and mandatory start gate
- Read START_HERE.md, STATE.md, REGISTRY.json, this protocol and RESEARCH_PARTS.md, then the latest canonical Agent Handover, Master Decision Book, 520-detail register, migration reservations, Board and work-split protocol. Verify current canonical HEAD, branch/PR heads, permissions, relevant CI and deployment evidence; stale or inaccessible evidence is UNKNOWN/UNVERIFIED, never fabricated.
- Authority order: explicit current Owner decisions + canonical Decision Book; canonical handover/Board and approved lane protocols; this benchmark supplement; individual reports. Resolve contradictions with the designated coordinator/Owner and record them; no unilateral policy rewrite.
- Every task must have unique packet/feature ID, claim owner, scope/path list, branch, base SHA, dependencies and Board row BEFORE editing. No parallel writes to the same paths or reservation. Read-only research may run in parallel on clearly nonoverlapping packets. If Board or source access fails, record BLOCKED; no unclaimed code edits. Recheck claims before committing. Do not take over abandoned work without coordinator approval and current-head reconciliation.

## M02 — Preservation is a hard gate, not a preference
- No original option, field, report, workflow, permission, control, rule, calculation, industry behavior, decision or intended business result may disappear. Retain original IDs and evidence. Freeze the existing 1,246 PaperOps IDs and 1,000/246 ownership; preserve 463 legacy blobs and every original route/action. Do not silently delete draft/planned items.
- Replacement/refactor/reorganization is permitted only with explicit old-to-new crosswalk, equivalent or superior outcomes, migrated settings/data and rollback, negative and positive regression tests. Menu relocation, progressive disclosure and authorized role visibility are allowed; prove authorized users can still find and execute every original option. Existing security and invariants cannot be toggled off.
- Every discovered requirement must have a recorded disposition even if deferred or inapplicable. Deferred/blocked is not deleted; material business-policy change or removal requires explicit Owner decision, recorded in Decision Book. Missing evidence means investigation, not a missing-feature verdict.
- New features use existing Auth, Master, Stock, Money, Approval, Audit, Control and canonical posting contracts; no duplicate ledger/engine; follow DEC-08 for feature control. No arbitrary executable AI-generated rules. Protect customer isolation and Goal 1/Goal 2.
- Upstream code is a reference; independently implement behavior unless licensing and obligations have been explicitly reviewed. No copy of GPL code into CORE10 by default.

## M03 — Evidence and measurable modernization
- For each atomic capability record original IDs, original purpose/outcome and source; pinned upstream repo/ref/path/symbol/line/blob or release/issue; CORE10 branch/SHA/path/symbol/test/CI; exact evidence quality (inventory vs inspected source vs executed test vs hosted vs Owner acceptance). Keep alternatives, risks and open questions. Never conflate declaration, design, draft, trunk, staging, production, Owner acceptance.
- Compare existing implementation even if feature exists: algorithms, correct outputs, permissions, idempotency/races, locks, latency/query count, throughput, UI steps/accessibility, reliability, cost. Define baseline on fixed synthetic fixtures; measure before/after using same workload and environment. Set targets after baseline. Report p50/p95/p99, errors, query plans when relevant; verify 10/100/400-site workloads separately from provisioning capacity. No invented speed claims or ranking.
- For Money/Stock/production require exact decimal and ledger/source/audit parity, duplicate/replay/rollback and cross-scope negatives. No benchmark speed-up qualifies if correctness, security, traceability or original behavior regresses.
- For reverse comparison distinguish core ERPNext/Frappe/HRMS, supported releases, optional apps, custom extensions and external services. State comparator scope and search limitations. Classify unique-candidate vs equivalent vs differently implemented; no absence claim without sufficiently scoped evidence.

## M04 — Single registry, multi-agent maintenance
- Canonical records are REGISTRY.json, STATE.md and Decision Book/Board (authority for policy/ownership respectively). PR #157 branch is temporary research source until canonical integration. Only designated research registry maintainer writes central registry/state on its branch; other agents submit packet-specific evidence/diffs in their own claimed branches or attach source-cited reports; never overwrite concurrent registry updates.
- Stable BENCH IDs: append only, never recycle; expand grouped parent into atomic child IDs and keep parent. Maintain old-to-new maps; entries require domain, original IDs or explicit mapping pending, evidence, disposition, separate research/delivery status, owner/claim, dependencies, action, acceptance, measurement/unknowns and next action. Corrections keep previous evidence and reason in log. Link duplicates rather than deleting. Before publishing compare old/new ID sets, reject any lost original ID or BENCH ID, invalid duplicate or missing required field, unexplained status advancement or cross-lane path change. Initial seeds do not equal complete inventory.
- All research outputs use a packet ID and source snapshot; do not create competing master spreadsheets/registries. Proposed updates returned to coordinator for deduplication and atomic merge, based on current HEAD. If another agent updated a shared document, reconcile first; no force-push.
- At START: Board CLAIMED, record base and assigned paths. During: IN_PROGRESS, update exact pushed SHA and tested scope. At each meaningful checkpoint (at latest after 2–4 substantial slices per DEC-10), commit/push branch, record evidence/test outcomes, update Board and submit STATE/registry delta. At STOP/interruption: always record actual completed/partial/blocked, uncommitted files, exact next action, dependencies and next claim; never report unsaved work as completed. For research-only tasks explicitly say NO PRODUCT CODE / CI NOT RUN where true. At HANDOFF: include latest links and unresolved risks; successor re-verifies them.
- Board status vocabulary remains CLAIMED/IN_PROGRESS/READY_FOR_INTEGRATION/INTEGRATED/RETURNED/BLOCKED; do not confuse with research/delivery maturity. Ready for integration requires exact evidence and scoped review, not automatic merge permission. Only canonical integrator marks integrated. Release statuses require corresponding evidence.
- Agent result format (mandatory): packet/claim | timestamp UTC | source SHAs | findings and old-to-new IDs | disposition | exact files/diff | tests and outcomes (including failures/skips) | measured before/after or NOT MEASURED | commit/PR | blockers | next action | Board row. Owner report in concise Bangla.

## M05 — Research / thinking / build boundary
- Deep Research: multi-source, read-only investigation; cite original sources, enumerate all requested topics, deliver atomic findings and coverage/unavailable-source report. No merge, deploy, live write, new policy or speculative build. If connector source unavailable, use supplied exported copy with date/ref, explicitly mark missing; never infer.
- Deep Thinking (High/Extra High if available): reconcile evidence/contradictions, check coverage, alternatives and risks; turn findings into prioritized testable work orders, not a substitute for running tests. Independent reviewer challenges claims and verifies exact evidence; do not fabricate subagents.
- Codex/Claude Code/authorized builders: implement only approved nonconflicting slices; run tests and actual performance measurements in disposable environments, commit/push. Follow PG17, RLS/ACL, migration and rollback, signed-context, mobile bn/en, no-loss gates in START_HERE. Preserve all protected projects and branch permissions. Do not jump migration order, weaken tests, publish secrets, or touch main/production without authority. Existing ongoing work continues; research is not a release freeze.
- If any mandatory gate fails: mark BLOCKED/RETURNED with exact reason and next remediation; no ready/merge/deploy until resolved. A research finding may become BUILD_READY only when sources, old behavior, target architecture, owner/claim, dependencies, file path, acceptance and known risks are explicit. A build cannot be declared delivered before corresponding exact-head test evidence.

## M06 — Long-term enforcement and audits
- At each research-part completion reconcile row counts, duplicate/unmapped IDs, source coverage, unresolved contradictions, evidence and blockers. At each build PR review no-loss crosswalk, policy/role/data invariants, original tests, new tests and migration/rollback. At each release verify current staging and deployed artifact hashes, scoped rollback and acceptance. Review upstream releases periodically through a separately authorized scheduled or manual task; no background activity is assumed.
- Coordinator maintains one prioritized queue, not overlapping review-only loops. Reopen evidence when upstream/core head materially changes, retain old snapshot and update delta only; no full restart. Independent reviewer checks high-risk financial/security or no-loss decisions before integration.
- Proposed executable enforcement (not implemented by this docs-only change): canonical integrator adds registry schema/unique-ID and previous-ID preservation CI, source evidence/status checks, required PR checklist/crosswalk, and protected-branch review gate consistent with existing permissions. Separate claimed task; do not modify shared CI/branch protection without authorization. Until then these are mandatory documented review gates, not technically enforced by GitHub. Report enforcement maturity explicitly.
